# 🔌 Сокет (Socket)

> [!abstract] Суть одной фразой
> Сокет — это программный интерфейс, конечная точка сетевого взаимодействия, через которую процессы обмениваются данными. Он абстрагирует сетевые протоколы, позволяя приложению отправлять и получать данные, не вдаваясь в детали реализации нижележащих уровней [[Модель OSI  (Open Systems Interconnection)|модели OSI]].

Для специалиста по ИБ сокет — это ключевой объект аудита, мониторинга и расследования инцидентов: именно сокеты связывают приложения с сетевыми портами и файловой системой.

---

## 📌 Два принципиально разных типа сокетов

### 🌐 Сетевые сокеты (Internet Sockets)
Используются для взаимодействия процессов по сети через протоколы TCP или UDP. Идентифицируются комбинацией **IP-адреса и номера [[Порт (сетевой)|порта]]**. Именно их мы видим в выводе `ss -tuln`, когда проверяем открытые порты.

- **TCP-сокет:** обеспечивает надёжную потоковую передачу данных (HTTP, SSH).
- **UDP-сокет:** обеспечивает быструю передачу без гарантий доставки (DNS, DHCP).

### 📁 Unix-сокеты (Unix Domain Sockets)
Используются для взаимодействия процессов **в пределах одного хоста**. Вместо IP-адреса и порта они идентифицируются специальным файлом в файловой системе, который имеет тип `s` в выводе `ls -la`. Работают быстрее сетевых сокетов, так как не проходят через сетевой стек.

- **Пример:** `/var/run/docker.sock` — сокет Docker API.
- **Пример:** `/run/mysqld/mysqld.sock` — сокет MySQL для локальных подключений.

---

## 🔍 Как выглядит сокет в файловой системе

> `ls -la /var/run/docker.sock`
> `srw-rw---- 1 root docker 0 мар 10 12:00 /var/run/docker.sock`

Первый символ `s` указывает, что это файл типа **socket**. Права доступа определяют, кто может взаимодействовать с этим сокетом.

---

## 🛡️ Значимость для специалиста по ИБ

- **Unix-сокет Docker (`docker.sock`):** если злоумышленник получит доступ к этому файлу, он сможет управлять Docker-демоном от имени root: запускать контейнеры, выходить из них, читать чужие данные. Я всегда проверяю права на этот сокет при аудите.
- **Сетевые сокеты в состоянии `LISTEN`:** каждый слушающий сокет — это потенциальный вектор атаки. Я проверяю, какие процессы их открыли (`ss -tuln -p`), и отключаю неиспользуемые.
- **Сокеты как средство обхода:** злоумышленники могут создавать скрытые сокеты для обратных шеллов, маскируя их под системные.

## 🔧 Инструменты для аудита сокетов

- **`ss -tuln -p`** — показать все сетевые сокеты в состоянии LISTEN с информацией о процессе.
- **`ls -la /var/run /tmp`** — найти подозрительные Unix-сокеты.
- **`lsof -i`** — показать, какие процессы используют сетевые сокеты.

## 🔗 Связи

- [[Порт (сетевой)]] — порт, который привязывается к сетевому сокету.
- [[ss]] — утилита для аудита сетевых сокетов.
- [[lsof]] — утилита для поиска открытых файлов, включая сокеты.
- [[Типы файлов в Linux]] — сокет как тип файла (`s`).
- [[iptables]] — фильтрация трафика, который идёт через сетевые сокеты.

## 💬 Ответ на собеседовании (кратко)

> «Сокет — это конечная точка обмена данными между процессами. Бывают сетевые (TCP/UDP, идентифицируются IP и портом) и Unix-сокеты (файлы в файловой системе). Я проверяю слушающие сокеты через `ss -tuln`, а опасные Unix-сокеты, такие как `docker.sock`, — через `ls -la` на предмет избыточных прав».

## ❓ Самопроверка

1. **Чем Unix-сокет отличается от TCP-сокета?** 👉 Unix-сокет существует как файл в файловой системе и работает только локально, TCP-сокет использует IP-адрес и порт для связи по сети.
2. **Как посмотреть все слушающие TCP-сокеты на хосте?** 👉 `ss -tln`.
3. **Почему доступ к файлу `/var/run/docker.sock` опасен?** 👉 Он позволяет управлять Docker-демоном от имени root, что даёт злоумышленнику полный контроль над контейнерами.
