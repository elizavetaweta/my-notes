# 🔐 TLS (Transport Layer Security)

> [!abstract] Суть одной фразой
> TLS — криптографический протокол, обеспечивающий защищённую передачу данных между клиентом и сервером через Интернет. Он гарантирует [[Конфиденциальность]], [[Целостность]] и [[Аутентификация|аутентификацию]] сторон, благодаря чему на нём строятся HTTPS, защищённая почта, мессенджеры и множество других сервисов.

TLS работает поверх TCP ([[Протоколы транспортного уровня TCP и UDP]]) и состоит из двух основных фаз:

1. **[[Рукопожатие|Рукопожатие]] (handshake)** — согласование параметров и проверка подлинности.
2. **Обмен записями (record)** — шифрование передаваемых данных с контролем целостности.

---

## 📌 Как работает TLS (упрощённо)

### Фаза рукопожатия (handshake) — установка защищённого канала

1. **ClientHello** — клиент посылает список поддерживаемых версий TLS,[[Cipher Suite (Набор шифров)]] и случайное число.
2. **ServerHello** — сервер выбирает конкретную версию и cipher suite, отправляет своё случайное число и собственный сертификат ([[Инфраструктура открытых ключей (PKI)]]).
3. **Проверка сертификата** — клиент проверяет сертификат по цепочке доверия до корневого удостоверяющего центра.
4. **Обмен ключами** — стороны договариваются об общем сессионном ключе с помощью асимметричного алгоритма ([[ECC]] на Curve25519 или P‑256, либо классический [[RSA]]/DH).
5. **Финализация** — вычисляются симметричные ключи для шифрования и имитовставок, рукопожатие завершается проверочными сообщениями `Finished`.

### Фаза передачи данных (record) — защита трафика

Весь дальнейший транспорт шифруется симметричным алгоритмом (например, [[AES]]-GCM или [[ChaCha20]]-Poly1305) и защищается кодом аутентификации (MAC), гарантирующим [[Целостность]].

## 🔑 Версии и cipher suites

### Актуальные версии

- **TLS 1.2** (2008) — всё ещё широко распространён. Поддерживает множество алгоритмов, однако допускает устаревшие (CBC, статический RSA, SHA‑1). При использовании необходимо явно отключать слабые наборы.
- **TLS 1.3** (2018, RFC 8446) — современный стандарт, обязательный для новых систем. Убраны все слабые алгоритмы, оставлены только безопасные:
  - **AEAD‑шифры**: AES‑GCM, ChaCha20‑Poly1305.
  - **Обмен ключами**: исключительно эфемерный Диффи‑Хеллман (DHE или ECDHE) с **Perfect Forward Secrecy** (PFS).
  - **Хеширование**: SHA‑256, SHA‑384.

> [!danger] Запрещённые версии
> SSL 2.0, SSL 3.0, TLS 1.0, TLS 1.1 полностью выведены из эксплуатации (RFC 8996). Их поддержка на сервере или клиенте считается критической уязвимостью.

### Рекомендованные cipher suites (TLS 1.3)

| Название (IANA)                   | Назначение                                      |
| --------------------------------- | ----------------------------------------------- |
| `TLS_AES_128_GCM_SHA256`          | Шифрование AES‑128‑GCM, хеш SHA‑256             |
| `TLS_AES_256_GCM_SHA384`          | Шифрование AES‑256‑GCM, хеш SHA‑384             |
| `TLS_CHACHA20_POLY1305_SHA256`    | Шифрование ChaCha20, аутентификация Poly1305    |
| `TLS_AES_128_CCM_SHA256`          | Для constrained‑устройств (IoT)                 |
| `TLS_AES_128_CCM_8_SHA256`        | Облегчённая версия предыдущего                 |

## 🔗 Связь с криптографическими понятиями

- **[[Симметричное шифрование]]** — AES, ChaCha20 (основное шифрование трафика).
- **[[Асимметричное шифрование]]** и **[[ECC]]** — обмен ключами и аутентификация (ECDHE, ECDSA).
- **[[Инфраструктура открытых ключей (PKI)]]** — доверие к сертификатам сервера (и клиента при mTLS).
- **[[Хеширование]]** — SHA‑256, HMAC (имитовставки, подпись Finished).
- **[[Электронная подпись]]** — подпись сертификата удостоверяющим центром.
- **[[Гаммирование]]** — используется в ChaCha20 и AES‑GCM (режим CTR).
- **[[Триада КЦД]]** — TLS обеспечивает конфиденциальность и целостность данных, а также аутентичность сервера (и опционально — клиента).

## 🧠 Значимость для специалиста по ИБ

- Я понимаю, что TLS — **основа безопасности веб-коммуникаций**, поэтому при аудите веб‑приложений первым делом проверяю поддерживаемые версии протокола и список cipher suites.
- Я требую **отключения TLS 1.0/1.1** и слабых наборов (CBC, static RSA, SHA‑1, NULL) на всех публичных и внутренних серверах.
- Я различаю **обычный TLS** и **mutual TLS (mTLS)** — последний добавляет аутентификацию клиента с помощью сертификата, что критично для межсервисного взаимодействия.
- Я слежу за актуальностью сертификатов и знаю, что сертификаты с RSA‑ключами короче 2048 бит или подписанные SHA‑1 недопустимы.
- Я умею **вручную проверять конфигурацию TLS** с помощью утилит командной строки (openssl, nmap, testssl.sh), чтобы быстро выявить слабые места.

## 🛠️ Инструменты и практические примеры проверки TLS

### 1. openssl s_client — ручная проверка соединения

- `-connect` (**connect**) — адрес сервера в формате `хост:порт`.
- `-servername` (**server name**) — имя хоста для расширения SNI (обязательно при нескольких виртуальных хостах на одном IP).
- `-tls1_2` (**TLS 1.2**) — принудительно использовать TLS 1.2.
- `-tls1_3` (**TLS 1.3**) — принудительно использовать TLS 1.3.
- `-ciphersuites` (**cipher suites**) — список предпочитаемых наборов шифров для TLS 1.3 (например, `TLS_AES_128_GCM_SHA256`).

```bash
# Проверка поддержки TLS 1.3 и просмотр сертификата
openssl s_client -connect example.com:443 -servername example.com -tls1_3
```

### 2. nmap — поиск поддерживаемых cipher suites

- `-p` (**p**ort) — указать целевой порт.
- `--script` (**script**) — выполнить скрипт NSE (Nmap Scripting Engine).

```bash
nmap --script ssl-enum-ciphers -p 443 example.com
```

Результат покажет оценку стойкости каждого набора и предупредит об использовании слабых шифров.

### 3. testssl.sh — полноценный аудит TLS-конфигурации

- `--quiet` (**quiet**) — сократить вывод.
- `--each-cipher` (**each cipher**) — тестировать каждый шифр индивидуально.

```bash
testssl.sh --quiet --each-cipher example.com
```

Утилита выдаёт цветовую оценку (зелёный / жёлтый / красный) для каждого проверяемого параметра, что удобно для быстрой оценки.

## ❓ Самопроверка

1. **Чем TLS 1.3 принципиально отличается от TLS 1.2?**  
   👉 Убраны слабые алгоритмы (CBC, статический RSA, SHA‑1), оставлены только AEAD‑шифры (GCM, ChaCha20‑Poly1305) и эфемерный обмен ключами (PFS обязателен). Рукопожатие стало быстрее (1‑RTT).

2. **Зачем в TLS используется и асимметричная, и симметричная криптография?**  
   👉 Асимметрия нужна для безопасного согласования сессионного ключа и проверки сертификата, а симметрия — для быстрого шифрования основного трафика.

3. **Что такое Perfect Forward Secrecy и почему оно важно?**  
   👉 Это свойство, при котором компрометация долговременного ключа сервера не позволяет расшифровать ранее записанный трафик. В TLS 1.3 PFS обеспечивается всегда за счёт использования эфемерных ключей (ECDHE).

4. **Какие инструменты вы используете для проверки конфигурации TLS на сервере?**  
   👉 `openssl s_client` — для ручной диагностики, `nmap --script ssl-enum-ciphers` — для оценки наборов шифров, `testssl.sh` — для комплексного аудита с цветовым отчётом.
